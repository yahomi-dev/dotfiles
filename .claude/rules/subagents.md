# サブエージェントへの委譲

## 委譲するかの判断

- 作業に着手する前に、サブエージェントに委譲すべきかを都度判断する
- 広範な探索、大量のファイルの読み込み、並列で進められる調査など、コンテキストの消費が大きい作業は委譲する
- 少量の編集や数ファイルの読み取りで済む作業は直接行う (委譲のオーバーヘッドの方が高くつくため)

## モデルと effort

Agent を呼ぶときは `model` と `effort` を必ず明示する。

- 実装: `model: opus`、`effort: xhigh`
- 設計が必要な部分 (設計書の下書き、設計判断を含む作業): `model: fable`、`effort: high`。構造に関わる設計は `xhigh`
- 定型の調査と探索: `model: sonnet` か `haiku`
- 設計と実装が混ざる作業は、設計の部分を先に確定してから実装を任せる

## 依頼文に書くこと

- 調査を並列で任せるときは次の 3 点を書く (入れ子の起動で利用上限に当たった前例がある)
  - サブエージェント (Agent ツール) は使わず、自分で調べる
  - 1 項目終わるごとに結果ファイルへ追記する
  - 時間がかかる項目は「見つからない」で打ち切る
- CI の pipeline の完了をサブエージェントに監視させない。依頼文に「pipeline が green であること」と書かず、push して MR を作った時点で報告させる。結果は親が API で 1 回だけ確認する

## 自分で CI を監視するとき

- 監視する対象を ID で 1 つに決めてから待つ (コミットの sha から pipeline の ID を特定する)。「最新の何本かの中の最初の 1 件」のような推測はしない
- ループは背景に回す前に前景で 1 回流し、出力の形を確認する。API やパースの失敗が続いたら、エラーを出してすぐ抜ける
- 間隔は 10〜15 秒。待つのは数分で終わるものだけにする
- CLI の表示 (「Merged!」等) を信じず、state を API で確認する
- 結果が次の行動を変えないなら監視しない
